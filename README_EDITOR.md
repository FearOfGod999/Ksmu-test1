ОСНОВНЫЕ ИЗМЕНЕНИЯ
— Произвольное начало учебного года (четыре цифры, 1900–9998), например 2037 = 2037/38. Сервер принимает формат 2037-2038, но больше не ограничен 2029 годом.
— Выбор осеннего и весеннего семестра; черновики разных периодов не смешиваются.
— Редактирование расписания возможно только после подтверждения сервером роли editor/publisher/admin и полномочий на каждую группу. Проверка в интерфейсе НЕ является единственным барьером: API повторяет проверку роли, scope, данных и подтверждения полной замены.
— Гость может просмотреть Excel, ошибки и отличия, скачать JSON-черновик и CSV-отчёт, но не может заменить расписание ни на сервере, ни локальной кнопкой.
— Мастер: перетаскивание файла, фильтр отчёта по группе, центрирование кнопок, статус прав, мягкие анимации с поддержкой Reduced Motion.
— Утверждение и публикация версии — отдельная серверная операция для publisher/admin; режим проверки другим сотрудником сохранён.
— Все 242 группы и основное расписание сохранены побайтово, 1103/1203/1303 защищены заглушками.

ВАРИАНТЫ СБОРКИ
1. OFFLINE ZIP — распакуйте, откройте index.html в Chrome/Edge. Вся навигация/просмотр и локальные ДЗ/модули доступны. Импорт можно анализировать, но НИ ОДИН пользователь не сможет применить его к расписанию в этом автономном файле. Нет обращения к Supabase или /api.
2. SERVER SOURCE ZIP — исходники с функциями авторизации и проверки публикаций. НЕ ГОТОВ К ПУБЛИЧНОМУ РАЗВЁРТЫВАНИЮ без тестового HTTPS-сервера, БД и настроенных прав. Серверная форма e-mail/пароль использует прежний Supabase Auth, но новый API должен проверять JWT и таблицу kgmu_editors. Для бота отдельная авторизация. НЕ РАЗМЕЩАЙТЕ НА БОЕВОМ СЕРВЕРЕ БЕЗ ОТДЕЛЬНОГО ТЕСТИРОВАНИЯ.

СЦЕНАРИЙ РАБОТНИКА
1. Профиль → серверный вход с правами редактора.
2. Импорт → год, семестр, масштаб (группа/курс/направление).
3. Перетащить нормализованный XLSX или выбрать файл.
4. Сверить ошибки, количество записей и список исчезающих занятий. С помощью поиска найти нужную группу, скачать CSV-отчёт.
5. Указать дату утверждения и комментарий, подтвердить полную замену, если требуется.
6. Отправить пакет через защищённый API. Это не публикация.
7. Второй сотрудник с правами publisher/admin сверяет черновик и публикует его; предусмотрена история и откат.

ЗАМЕЧАНИЯ ПО БЕЗОПАСНОСТИ
— Нельзя выдавать роль через UI или по Telegram-нику. Права должны храниться в доверенной БД, редактироваться только администраторами с журналом выдачи.
— Публичный ключ Supabase не является сервисным секретом, но таблица kgmu_editors должна иметь корректную серверную модель прав/RLS: пользователь может читать только свои разрешения и не может сам создавать/изменять роли.
— Все действия записи на сервер требует TLS, серверной проверки личности, роли, области доступа и журналирования.
— Cloudflare D1/Pages Functions — текущий каркас. Для размещения на российском сервере придётся адаптировать функции и хранилище; юридическую оценку и проверку требований обработки данных проводит университет.
— У старых расписаний остаются спорные исходные строки (5303и, 8302и, 3401–3404); обновления по ним требуют проверки первоисточника.
— Исходные Excel-файлы со сложными циклами и формулами не следует публиковать без предварительной нормализации и проверки секретариатом.
— Реальную интеграцию с Supabase/TG и право выдачи ролей в боевой среде здесь не проверяли.
